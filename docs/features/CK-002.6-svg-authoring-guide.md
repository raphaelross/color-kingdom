# CK-002.6 SVG Authoring Guide

## Purpose
This guide defines the production SVG contract for polished Color Kingdom pages using the existing `SvgColoringRenderer` pipeline.

The objective is reliable child-friendly coloring behavior with visually rich line art, without changing renderer architecture.

## Required Baseline
- Use a stable source-authored coordinate system with explicit `viewBox`, `width`, and `height`.
- For source-fidelity conversions, preserve original dimensions and path geometry.
- Use path-based artwork for all relevant visual geometry.
- Every colorable region must be a closed path with a unique stable `id`.
- Every interactive path must include `data-role="colorable"`.
- Every non-interactive detail path should include `data-role="static"`.

## Region IDs
- IDs are canonical and must stay stable once released.
- Use lowercase kebab-case IDs.
- Recommended pattern: `subject-part-variant`.
- Examples:
  - `kitten-ear-left`
  - `flower-right-center`
  - `deco-star-left`

## Metadata Requirements
- Colorable path:
  - `id` (non-empty, unique)
  - `data-role="colorable"`
  - optional `data-region-name`
- Static path:
  - `data-role="static"`
  - `id` optional unless needed for authoring/debug readability

## Closed Path Requirement
- Colorable regions must be closed, area-bearing paths suitable for `Path.contains` hit testing.
- Do not mark open stroke-only paths as colorable.
- Tiny accents should remain static.

## Tap-Target Guidance
- Interactive regions should be comfortably tappable at default zoom.
- Practical minimum guideline for colorable region bounds:
  - approximately 18 x 18 SVG units as an absolute lower bound
  - prefer larger targets for child usability
- If a detail is too small or thin, keep it static.

## Colorable vs Static Detail Rules
Use `data-role="colorable"` for meaningful child-customizable areas.

Use `data-role="static"` for fine visual polish details, including:
- eyelashes
- whiskers
- eye highlights
- fur strokes
- tiny stars/sparkles
- leaf veins
- hatch accents

## Stroke And Fill Conventions
- Colorable paths should default to transparent fills.
- Static line art should use clear dark outlines suitable for coloring-book readability.
- Keep line style consistent per page.
- Do not rely on custom cap/join semantics for correctness.

## Z-Order And Overlap Rules
- Author draw order intentionally.
- If colorables overlap, top-most region wins tap resolution.
- Avoid accidental overlap between adjacent colorable regions.
- Place static details above filled regions when decorative overlay is desired.

## Grouping And Nesting
- Groups are allowed for organization and role/style inheritance.
- Keep nesting shallow and readable.
- Avoid deep nesting that complicates debugging.

## Transform Restrictions
- Do not rely on `transform` attributes in CK-002.6 content.
- Bake transforms into path coordinates during SVG preparation.

## Unsupported/Restricted Geometry
CK-002.6 content should avoid relying on the following for interactive correctness:
- `circle`
- `ellipse`
- `rect`
- `polygon`
- `polyline`
- `line`
- `transform`
- `clipPath`
- `mask`
- complex fill-rule-dependent holes

Convert required geometry to path data during asset preparation.

## Complexity Tiers (Content Planning)
These tiers are planning classifications only; no model field is required yet.

- Easy: 8-15 colorable regions
- Standard: 15-30 colorable regions
- Detailed: 30-50+ colorable regions

## Benchmark Requirement
`Lovely Kitten` is the CK-002.6 polished benchmark page.

It demonstrates:
- high-fidelity static line art preserved from source artwork
- simplified interactive layer with exactly five production colorable regions for the POC
- preserved source coordinate system (`viewBox="0 0 1133 1388"`, `width="1133"`, `height="1388"`)
- compatibility with current parser/renderer/hit-testing/persistence behavior

## Validation Workflow
Before integrating a new page:
1. Validate SVG contract via automated validator tests.
2. Verify model region IDs exactly match SVG colorable IDs.
3. Verify no unsupported geometry or transforms.
4. Verify representative hit-testing and coloring interactions.
5. Verify persistence and My Creations progress behavior.
